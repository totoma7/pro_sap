연계 시나리오 & Punch-out

기술을 알았으니 이제 조립한다. 실제 프로젝트에서 어떤 인터페이스 목록이 나오고, Punch-out은 어떻게 동작하는가.

1. 전형적인 인터페이스 목록 (구매포털 ↔ SAP)

국내 구매포털 구축 프로젝트의 인터페이스 정의서는 대체로 아래 형태로 수렴한다. 마스터(기준정보)와 트랜잭션(거래문서)으로 나눠 보라.

마스터 동기화

인터페이스방향주기비고
공급업체(BP)포털 → SAP실시간(승인 시)포털 가입·심사 통과 → SAP BP 생성. 원본은 포털
자재 마스터SAP → 포털일배치 + 변경분원본은 SAP. 포털 카탈로그의 기준
단가 (Info Record/계약)포털 → SAP실시간(낙찰 확정 시)입찰 결과 반영. 유효기간 관리 주의
코스트센터 · WBSSAP → 포털일배치포털에서 계정 지정 입력용
구매조직 · 플랜트 등 조직SAP → 포털변경 시매핑 테이블의 기준

트랜잭션 흐름

1PR / 구매요청 포털 → SAP 간접구매 요청·승인 완료 → BAPI_PR_CREATE 또는 OData. 직접구매는 반대로 SAP PR을 포털로 보내 입찰에 부친다
↓
2PO 생성/변경 양방향 포털 발주 → SAP PO 생성(동기 BAPI, PO번호 즉시 회신) / SAP PO → 포털·공급사 통보(ORDERS·ORDCHG)
↓
3주문확인 · ASN 공급사 → SAP 포털에서 공급사가 수락/납기 회신(ORDRSP), 납품 통보(DESADV) → 입고 예정 정보로 활용
↓
4입고 결과 SAP → 포털 MIGO 입고 결과를 포털에 회신 → 공급사가 "검수 완료" 확인. 서비스면 SES 승인 결과
↓
5송장 · 지급 상태 양방향 포털 세금계산서 접수 → SAP 송장검증(INVOIC/BAPI) → 지급 예정일·완료를 포털로 회신해 공급사에 공개
패턴 읽기 결정은 포털에서, 원장은 SAP에서, 결과는 다시 포털로. 모든 트랜잭션 인터페이스가 "요청 → 기록 → 상태 회신"의 왕복 구조다. 회신(상태 동기화)을 빼먹으면 공급사 문의 전화가 구매팀으로 쏟아진다.

2. Punch-out — 외부 쇼핑몰을 내 구매 시스템처럼

사무용품·MRO처럼 품목이 수십만 개인 영역은 카탈로그를 내부에 복제하지 않는다. 대신 공급사 쇼핑몰로 "뚫고 나가서"(punch out) 장바구니만 들고 돌아온다.

1사용자가 구매 시스템에서 공급사 몰 클릭 구매 시스템이 로그인 정보를 담아 공급사 몰을 호출 — 사용자는 재로그인 없이 진입(SSO)
↓
2공급사 몰에서 쇼핑 검색·비교·장바구니 구성은 전부 공급사 몰의 UX 그대로. 단, 계약 단가가 적용된 전용 화면
↓
3"이송" 클릭 → 장바구니 반환 주문이 아니라 장바구니 데이터만 구매 시스템으로 돌아온다 (품목·수량·단가)
↓
4구매 시스템에서 승인 → PO 발행 반환된 장바구니가 PR이 되고, 승인 후 PO가 공급사로 송신된다. 통제는 우리 시스템이 쥔다

두 가지 표준

OCI (Open Catalog Interface)

  • SAP 진영의 고전 표준 (SRM 시절부터)
  • HTML 폼 필드로 장바구니 반환 — 단순
  • 국내 자체 구축 포털·MRO몰 연계에 여전히 널리 사용

cXML Punch-out

  • Ariba 진영 표준 — XML 메시지 기반
  • PunchOutSetupRequest → 쇼핑 → PunchOutOrderMessage
  • 이후 PO·송장도 cXML로 일관 처리 가능

3. 운영 설계 포인트 — 인터페이스는 만들 때보다 굴릴 때가 어렵다

설계 포인트문제 상황대책
중복 방지 (멱등성)타임아웃 후 재시도 → PO가 두 번 생성포털 문서번호를 키로 중복 체크, 동일 키면 기존 결과 회신
순서 보장PO 변경이 생성보다 먼저 도착선행 문서 존재 확인 후 처리, 미존재 시 대기 큐
오류 재처리마스터 미존재로 IDoc 51 오류오류 모니터링 + 마스터 보완 후 BD87 재처리 절차 문서화
상태 가시성"보냈는데 안 왔어요" 공방양 시스템 문서번호 매핑 테이블 + 통합 모니터링 화면
대사 (Reconciliation)장애 기간 유실 건 파악 불가일 단위 건수·금액 대사 배치, 차이 리포트 자동 발송
1-2차시와 연결되는 지점 송장 인터페이스가 멈추면 GR/IR 잔액이 쌓이고(1-2차시), 마스터 동기화가 어긋나면 모든 트랜잭션이 오류로 쌓인다(1-1차시). 운영 모니터링의 우선순위는 ① 마스터 ② 송장 ③ PO 순.

4. 3차시 핵심 요약

  • 대량·안정은 IDoc(비동기), 즉시 응답은 BAPI/OData(동기), Ariba는 CIG
  • 인터페이스 목록은 마스터 동기화 + 트랜잭션 왕복으로 수렴한다
  • 모든 트랜잭션은 "결정은 포털 → 원장은 SAP → 상태 회신"의 왕복 구조
  • Punch-out은 카탈로그 복제 대신 장바구니만 가져오는 방식 (OCI/cXML)
  • 운영의 생명선: 멱등성 · 순서 보장 · 오류 재처리 · 일일 대사
