심화 1

IDoc 깊이 보기 — 세그먼트 구조와 운영 실무

3차시에서 "봉투"라고 했던 IDoc을 열어본다. PO IDoc(ORDERS05)의 실제 구조, 상태 코드의 생애주기, 운영 트랜잭션까지.

1. Basic Type — 같은 메시지, 버전이 다르다

메시지 타입(ORDERS)은 "용도"고, Basic Type(ORDERS05)은 "구조 버전"이다. 숫자가 클수록 신버전이며 세그먼트가 추가된다. 연계 정의서에는 항상 둘을 함께 쓴다: ORDERS / ORDERS05.

2. ORDERS05 세그먼트 해부 — PO 한 건이 이렇게 생겼다

EDI_DC40 (제어 레코드)발신 파트너·수신 파트너·메시지 타입·Basic Type — "겉봉투"
E1EDK01 — 문서 헤더통화, 환율, PO 번호(BELNR). 문서당 1개
E1EDKA1 — 파트너 (반복)PARVW 구분: AG=발주처, LF=공급사, WE=납품처. 같은 세그먼트가 역할만 바꿔 반복된다
E1EDK02 — 참조 번호QUALF 구분: 001=PO번호, 011=견적번호 등 — 퀄리파이어 패턴
E1EDK14 — 조직 정보구매조직·구매그룹·문서유형(1-1, 1-3차시의 그 값들이 여기 실린다)
E1EDP01 — 품목 (반복)수량·단위·플랜트. 품목 수만큼 반복 — 하위에 자식 세그먼트를 거느린다
E1EDP20 — 납품 일정납기일·분할 납품 회차 (제조 SA 연계의 핵심)
E1EDP19 — 품목 식별QUALF 001=우리 자재코드, 002=공급사 품번 — 양쪽 코드가 함께 실린다
E1EDP05 — 가격 조건단가·할인·부대비 (Condition 단위)
E1EDS01 — 합계총액 검증용
읽는 요령 — 퀄리파이어 패턴 SAP IDoc은 필드를 늘리는 대신 같은 세그먼트를 구분값(QUALF/PARVW)으로 반복시킨다. 매핑 정의서에서 "E1EDKA1의 LF만 골라 공급사 코드로 매핑" 같은 조건 매핑이 끝없이 나오는 이유다.

3. 상태 코드의 생애주기

Outbound (SAP → 외부) 01 생성 → 30 송신 준비 → 03 포트로 전달됨 → (수신측 ACK 쓰면) 12 전달 확인 / 11 오류
↓
Inbound (외부 → SAP) 50 수신 → 64 처리 대기 → 53 전기 성공 / 51 전기 오류 ← 운영자가 매일 보는 숫자
함정 — 상태 03은 "성공"이 아니다 03은 "SAP 밖으로 나갔다"는 뜻이지 상대가 받았다는 뜻이 아니다. 미들웨어 장애면 03인데 포털에는 없는 상태가 된다. 그래서 일일 건수 대사(3-2차시)가 필요한 것.

5. 실습 시나리오 — 머릿속으로 한 번 돌려보기

1상황 포털에서 "어제 PO 3건이 안 들어왔다"는 문의. SAP은 ORDERS05 아웃바운드로 PO를 보낸다
↓
2WE02로 조회 어제 날짜 + ORDERS 필터. 3건 발견 — 상태 03. "SAP은 정상 송신" 확인
↓
3미들웨어 추적 CPI/EAI 모니터에서 해당 건 조회 → 포털 API 타임아웃으로 실패 확인. 미들웨어 재전송
↓
4재발 방지 미들웨어 재시도 정책 + 일일 건수 대사 리포트에 "03인데 포털 미수신" 항목 추가
핵심 IDoc 장애 분석은 항상 "어느 구간까지 갔는가"를 상태 코드로 좁히는 게임이다. SAP 내부(51) / 송신 경계(03 이후) / 미들웨어 / 상대 시스템 — 4개 구간 중 하나로 반드시 좁혀진다.
