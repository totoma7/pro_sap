심화 4

페이로드로 보는 매핑 — 같은 PO, 두 가지 언어

개념은 끝났다. 이제 실제 데이터를 본다. 동일한 PO 한 건을 IDoc(ORDERS05)과 cXML(OrderRequest)로 나란히 놓고 필드 단위로 대응시킨다.

0. 예제 거래

한울전자(구매조직 1100)가 대한정밀(공급사 코드 VND10023)에게 PO 4500012345를 발행. 품목 1건 — 베어링(자재 M-7733, 공급사 품번 DH-BRG-77) 500 EA, 단가 1,200원, 납기 2026-06-30, 납품처 평택공장(P100).

1. IDoc ORDERS05 원문 (발췌)

SAP → 포털 · WE02에서 보는 모습 
-- 제어 레코드 (EDI_DC40) --
MESTYP = ORDERS      IDOCTP = ORDERS05
SNDPRN = SAPECC      RCVPRN = PORTAL

E1EDK01                      문서 헤더
  CURCY  = KRW
  BELNR  = 4500012345      PO 번호

E1EDK14  QUALF=014 ORGID=1100   구매조직
E1EDK14  QUALF=012 ORGID=ZNB    문서유형(포털 전용)

E1EDKA1  PARVW=LF  PARTN=VND10023  공급사
E1EDKA1  PARVW=WE  PARTN=P100      납품처(평택)

E1EDP01                      품목 10
  POSEX  = 00010
  MENGE  = 500   MENEE = EA
  WERKS  = P100
  E1EDP20  EDATU=20260630 WMENG=500   납기·수량
  E1EDP19  QUALF=001 IDTNR=M-7733     우리 자재코드
  E1EDP19  QUALF=002 IDTNR=DH-BRG-77  공급사 품번
  E1EDP05  KOTXT=총액 BETRG=600000     가격 조건

E1EDS01  SUMID=002 SUMME=600000      합계 검증

2. 같은 PO의 cXML OrderRequest (발췌)

Ariba Network → 공급사 · CIG 변환 후 
<cXML>
  <Header>
    <From><Credential domain="NetworkID">AN0100012345</Credential></From>
    <To>  <Credential domain="NetworkID">AN0100067890</Credential></To>
  </Header>
  <Request>
    <OrderRequest>
      <OrderRequestHeader orderID="4500012345" type="new">
        <Total><Money currency="KRW">600000</Money></Total>
        <ShipTo><Address><Name>한울전자 평택공장</Name>...</ShipTo>
        <Extrinsic name="PurchasingOrg">1100</Extrinsic>  <!-- 커스텀 -->
      </OrderRequestHeader>
      <ItemOut quantity="500" lineNumber="10" requestedDeliveryDate="2026-06-30">
        <ItemID>
          <SupplierPartID>DH-BRG-77</SupplierPartID>
          <BuyerPartID>M-7733</BuyerPartID>
        </ItemID>
        <ItemDetail>
          <UnitPrice><Money currency="KRW">1200</Money></UnitPrice>
          <UnitOfMeasure>EA</UnitOfMeasure>
        </ItemDetail>
      </ItemOut>
    </OrderRequest>
  </Request>
</cXML>

3. 필드 매핑 표 — 매핑 정의서의 실제 모습

비즈니스 항목IDoc (ORDERS05)cXML (OrderRequest)변환 주의
PO 번호E1EDK01-BELNROrderRequestHeader@orderID—
통화E1EDK01-CURCYMoney@currency헤더 1곳 ↔ 금액마다 반복
공급사E1EDKA1[PARVW=LF]-PARTNHeader/To CredentialSAP 코드 ↔ Ariba Network ID 변환 테이블 필요
납품처E1EDKA1[PARVW=WE]ShipTo/Address코드 ↔ 주소 전문 — 마스터 참조 변환
품목 번호E1EDP01-POSEX (00010)ItemOut@lineNumber (10)선행 0 제거 — 단골 버그
수량/단위MENGE / MENEE (EA)@quantity / UnitOfMeasureSAP 내부 단위 ST ↔ ISO 단위 PCE 변환 주의
납기E1EDP20-EDATU (20260630)@requestedDeliveryDate (2026-06-30)날짜 포맷 + 타임존
자재/품번E1EDP19 QUALF 001/002BuyerPartID / SupplierPartID둘 다 싣는 것이 정석 — 한쪽만 보내면 상대가 매칭 불가
단가E1EDP05 (조건 단위)UnitPrice (품목 속성)IDoc은 할인·부대비가 조건별 분리 — 합산 규칙 정의 필요
구매조직E1EDK14[QUALF=014]Extrinsic "PurchasingOrg"표준에 없음 → 커스텀(Extrinsic)
표에서 배우는 매핑의 3가지 패턴 ① 구조 차이(헤더 1곳 ↔ 반복) ② 코드 체계 차이(변환 테이블) ③ 표준에 없는 항목(Extrinsic/Z-필드). 어떤 인터페이스든 매핑 이슈는 결국 이 셋 중 하나다.

4. 실전 Q&A — 현장에서 받는 질문들

Q1. 포털에서 보낸 PO 금액과 SAP PO 금액이 1원 다르다. 왜?
십중팔구 반올림 규칙 차이다. 부가세 계산(품목별 반올림 vs 합계 후 반올림), 단가 소수점 자릿수, 통화 환산 시점이 양쪽에서 다르면 1원 차이가 난다. 해법: 금액 계산의 기준 시스템을 하나로 정하고(보통 SAP), 상대는 계산하지 말고 받은 값을 그대로 쓴다. 세금계산서 역발행(5차시)이 이 문제를 구조적으로 없애는 방법이기도 하다.
Q2. 공급사 코드가 포털과 SAP에서 다른데, 변환 테이블은 누가 관리하나?
변환 테이블의 관리 주체와 위치를 하나로 — 보통 미들웨어(CIG/CPI)나 포털 한 곳. 양쪽에 복사해 두면 반드시 어긋난다. 그리고 신규 협력사 등록 흐름(포털 승인 → SAP BP 생성, 1-1차시)에 변환 테이블 자동 등록을 끼워 넣어야 운영 중 누락이 없다. "BP는 생겼는데 매핑이 없어 PO 송신 실패"가 단골 장애다.
Q3. PO를 변경하면 인터페이스는 어떻게 동작해야 하나?
SAP은 변경분 개념(ORDCHG)이고 Ariba cXML은 전체 재전송 + 버전 증가(orderID 동일, type="update")다. 매핑에서 ORDCHG를 받아 전체 문서를 재구성해 보내야 한다. 운영 관점 주의: 변경 IDoc이 생성보다 먼저 도착하는 순서 역전(3-2차시)과, 공급사가 이미 ASN을 쏜 품목의 수량을 줄이는 변경 — 이 두 가지는 차단 또는 경고 룰을 시스템에 넣는 게 안전하다.
Q4. 단위(EA/ST/PCE)가 꼬여서 수량 500이 5로 들어왔다. 어디를 봐야 하나?
단위 자체가 아니라 단위 변환 계수가 범인일 가능성이 높다. SAP 자재 마스터에는 "기본 단위 ↔ 구매 단위" 변환(예: 1 BOX = 100 EA)이 있는데, 인터페이스가 구매 단위 수량을 기본 단위로 잘못 해석하면 100배 차이가 난다. 점검 순서: ① 원본 페이로드의 수량·단위 ② 자재 마스터 단위 변환 계수 ③ 매핑 룰의 단위 코드 변환(ST↔PCE) — 이 순서로 어느 구간에서 값이 변했는지 좁힌다(심화 1의 구간 좁히기와 같은 발상).
Q5. 인터페이스 정의서에 꼭 들어가야 하는 항목은?
최소 9가지: ① 송수신 시스템·방향 ② 트리거(이벤트/배치) ③ 기술 방식(IDoc/API)과 메시지 구조 ④ 필드 매핑 표(위 3번 표 형식) ⑤ 코드 변환 테이블과 관리 주체 ⑥ 오류 처리·재처리 절차 ⑦ 멱등 키(중복 방지) ⑧ 처리량·성능 요건 ⑨ 대사 방법. 현장에서 빠져서 사고 나는 건 늘 ⑥⑦⑨ — 정상 흐름만 정의하고 비정상을 안 적은 정의서다.
학습 팁 위 두 페이로드를 종이에 놓고 매핑 표 없이 직접 선을 그어 보라. 10개 항목 중 8개 이상 연결되면 이 과정의 목표는 달성된 것이다.
